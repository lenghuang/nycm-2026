## User intent and product boundaries

The product is intentionally a race-execution companion, not a fitness tracker.

In scope:

- Manual landmark/phase changes.
- Per-phase run/walk cues, gel reminders, plan notes, and a glanceable race screen.
- Wall-clock timing that catches up after browser suspension or accidental refresh.
- Offline operation after an initial load.
- A local MP3 that begins at the Queensboro phase.
- Native iPhone local notifications for locked-screen cues.

Out of scope unless explicitly revisited:

- GPS, pace, or route tracking.
- Accounts, cloud sync, social features, and backend infrastructure.
- Automatic course progression.
- Remote push/APNs as a requirement.
- Live Activity implementation. It was discussed but deliberately deferred.

## Design history

### 1. Vanilla PWA first

The first version was a compact vanilla JavaScript PWA to optimize for a tiny runtime and no framework dependency. It included a wall-clock timer, a service worker, editable phases, Web Audio cues, browser notifications, and a silent audio element intended to keep an iOS audio session active.

### 2. TypeScript conversion

The user wanted maintainability before complexity accumulated. The app moved to strict TypeScript with a compiled browser output. This established typed phase data and persistent race state.

### 3. React/Vite/Bun workspace migration

The user expected the project to grow and preferred familiar tooling. The app moved to:

```text
apps/race-day       React + Vite + TypeScript + PWA + Capacitor
apps/data-pipeline  Reserved for future analysis/import work
packages/shared     Reserved for shared types and pure utilities
```

React was chosen for growing UI/state complexity; Vite for the development/build pipeline; Bun for workspace dependencies and app-local scripts. Mise now owns the top-level developer workflow and pins Bun.

### 4. Personalized NYCM plan

The default plan was replaced with the user’s detailed eleven-phase strategy:

2. 4th Avenue Brooklyn
3. Bedford
4. Pulaski Bridge
5. LIC
6. Queensboro Bridge
7. 1st Avenue Manhattan

9. Harlem

Phase data includes note, run/walk duration, gel interval, planned run/walk cycle count, starting mode, effort level, and music cue.

### 5. Pluggable configurations and test mode

The app no longer treats the NYC plan as one hard-coded configuration. A preset registry was added:

- `NYCM Strategy`
- `10 sec / 5 sec demo`

All durations are stored in milliseconds. The normal plan edits in minutes; the demo edits in seconds. The test preset is visibly marked as `TEST CONFIG`.

### 6. Effort-derived theme

The background gradient previously followed arbitrary per-landmark colors. The user asked for it to reflect effort. It now derives from a fixed semantic palette:

- `RECOVERY`
- `CONTROLLED`

### 7. Cue controls and interval progress

The race screen now has previous/next cue controls distinct from phase navigation. They move to the adjacent RUN/WALK boundary. Each phase has an editable planned number of run/walk cycles, displayed as completed and remaining intervals. These are planning targets only; phases never auto-advance.

## Critical platform finding

The browser PWA can preserve and reconstruct wall-clock time after a locked screen, but iOS may suspend browser JavaScript. This means browser timer callbacks, Web Audio cues, and page-created notifications are not reliable while locked.

Web Push is different from local notifications. Home Screen web apps can receive Web Push, but that requires an online push subscription and a server. It does not solve the offline-only race timer problem.

Apple’s native local-notification API schedules alerts with the operating system, which can deliver them even when the app is backgrounded or not running. That is the selected mechanism for locked-screen race cues.

Relevant references:

- [Apple: Scheduling a notification locally](https://developer.apple.com/documentation/UserNotifications/scheduling-a-notification-locally-from-your-app)
- [WebKit: Web Push for Home Screen web apps](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)
- [Apple: Live Activities](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities)

## Why Capacitor was selected

Capacitor was chosen over a full React Native or SwiftUI rewrite because it preserves the existing React UI and typed race-plan logic while exposing native iOS APIs.

Decision tradeoffs:

| Option | Decision | Reason |
| --- | --- | --- |
| Browser PWA only | Insufficient | Cannot reliably schedule offline locked-screen timer cues. |
| Capacitor | Selected | Smallest path from the existing React app to native local notifications and audio. |
| React Native | Deferred | Would require rebuilding the UI without a meaningful advantage for this focused app. |
| SwiftUI-only app | Deferred | Best if Apple Watch, widgets, Live Activities, or native interactions become the primary product; too large a rewrite for the present proof. |

Capacitor does not make browser timers magically reliable. Its value is the native bridge to iOS local-notification scheduling.

## Personal Team constraints

The free Xcode Personal Team is sufficient for a personal-device test. It is not suitable for ordinary app distribution or APNs remote push. The resulting phone installation must be re-provisioned/reinstalled after seven days.

The proof intentionally uses local notifications, not the Push Notifications capability and not APNs. The free Personal Team test should therefore be viable without paying for Apple Developer Program membership.

For a friend’s device, they should use their own Apple Account/Personal Team in Xcode to build to their own phone. Sharing a free-signed install is not a dependable distribution path.

Relevant reference:

- [Apple: Personal Team account limits](https://developer.apple.com/help/account/basics/about-your-developer-account)

## Current implementation state

`apps/race-day` contains:

- React/Vite source.
- PWA configuration and generated service worker during build.
- Typed preset registry in `src/configs/`.

Timing state uses persistent wall-clock anchors. An accidental refresh restores phase, pause state, interval position, and gel schedule. The app also checkpoints state during page hide and visibility changes.

### Native iOS shell

`apps/race-day/ios` was generated by Capacitor and contains the Xcode project and Swift Package manifest. Capacitor’s local-notifications plugin is present through Swift Package Manager.

The browser UI has a **Test locked-screen cue** action. In the native app it:

1. Requests native local-notification permission.
2. Schedules one `Race Day test` local notification ten seconds ahead.
3. Instructs the runner to lock the phone.

This is intentionally the minimal end-to-end proof. It does not yet schedule real race cues natively.

## Commands

Mise is deliberately slimmed down to one project task:

```bash
mise install
mise run ios
```

`mise run ios` does the following:

1. `bun install`
2. Builds the Vite app
3. Syncs web assets and plugins into the Capacitor iOS project
4. Opens the Xcode project

The app-level `package.json` retains granular Bun scripts for implementation work, but the intended human workflow is the one Mise command above.

## Physical iPhone test procedure

1. Install the full Xcode app, open it once, and accept its license. Command Line Tools alone are not enough.
2. Connect an unlocked iPhone via USB and trust the Mac if prompted.
3. Run `mise run ios`.
4. In Xcode, choose the `App` target.
5. In **Signing & Capabilities**, enable automatic signing and choose the user’s **Personal Team**.
6. Ensure the bundle identifier is unique if Xcode reports a collision.
7. Select the physical iPhone as the run destination and press Run.
8. If required, enable iPhone Developer Mode under **Settings → Privacy & Security → Developer Mode**, restart, then Run again.
9. Tap **Test locked-screen cue**, allow notifications, lock the phone, and wait ten seconds.

Expected result: iOS displays the `Race Day test` local notification while the phone is locked.
